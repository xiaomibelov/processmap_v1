# Правило ротации паролей и ключей (PASSWORD ROTATION RULE)

Ревизия 1 (восстановлено 2026-08-08). Действует для всех контуров (LLM, admin,
деплой, гейты, отчёты).

## 1. Секреты не публикуются

В репозитории, логах, тестах, гейт-артефактах, скринах, PR-описаниях и отчётах
**запрещено** размещать значения секретов: API-ключи LLM-провайдеров, пароли,
токены, приватные URL с кредами. Допустимо указывать только **факт наличия**
секрета и **факт ротации** (дата, кто ротировал, куда внесён).

## 2. Ключи вводит только владелец вручную

LLM-ключи (и иные провайдерские секреты) вносятся **только владельцем вручную
через админ-панель** (раздел LLM → Провайдеры). Агентам и скриптам запрещено
записывать реальные ключи в БД/файлы/окружение. Для локальных гейтов —
заведомо моковые значения (`sk-gate-mock`, `sk-bad`, `sk-supersecret-*-test`),
помеченные как тестовые.

## 3. В логах и файлах — только has_api_key + key_last4

API-ответы, экспорт, аудит-логи и отладочные выводы показывают ключи только
маскированно: `has_api_key: bool` и `key_last4: string` (последние 4 символа).
Полные значения, `base_url` с кредами и имена секрет-переменных со значениями
не выводятся. (Контроль: grep по диффам и отчётам на `sk-`, пароли, Bearer.)

## 4. Ротация

- Ключи LLM-провайдеров ротируются владельцем через админ-панель; в коде и
  миграциях ключей нет (seed-провайдер создаётся без ключа).
- Пароли пользователей — через механизм смены пароля; хэши вне логов.
- После инцидента (подозрение на утечку): немедленная ротация + запись факта
  ротации (без значений) в журнал изменений.

## 5. Нарушения

Найденный в репо/артефактах секрет считается скомпрометированным: удалить из
файла, ротировать значение, зафиксировать факт ротации (без значения).
