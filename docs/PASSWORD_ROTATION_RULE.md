# Правило ротации паролей и ключей (PASSWORD_ROTATION_RULE)

> Восстановлено 2026-08-17 в контуре AGENT-SVC Phase 5 (назначено ещё на Phase 3,
> файл отсутствовал в репозитории). Обязательно для всех агентов и контуров.

## 1. Публикация секретов запрещена

- В коде, тестах, логах, документации, PR, issue, чат-протоколах и артефактах
  верификации секреты (пароли, API-ключи, токены) **не публикуются**.
- Допустимое представление секрета в артефактах — только маскированное:
  `has_api_key: true/false` + `key_last4` (последние 4 символа).
  Это соответствует серверному контракту (`llm_store.mask_provider`).
- Если секрет случайно попал в лог/коммит/протокол — он считается
  скомпрометированным: владелец ротирует его, а артефакт вычищается.

## 2. Ввод и хранение ключей

- LLM-ключи вводит **владелец вручную** через админку
  (Админка → LLM → Провайдеры). Агенты не прописывают ключи в код и не
  коммитят их в репозиторий.
- Хранение ключей — только в БД (`llm_providers`) и/или `.env`
  (вне git). Файл `.env` не коммитится.
- Внутренние токены межсервисного взаимодействия (например,
  `AGENT_SVC_INTERNAL_TOKEN`) — через env, без публикации.

## 3. Ротация

- Ротация ключа выполняется владельцем: новый ключ вводится в админке
  (PATCH провайдера), старый отзывается у провайдера.
- После ротации сервисы подхватывают ключ без редеплоя: agent-сервис
  читает провайдеров из общей БД, кэш `resolve_model` — TTL 60 с
  (правка вступает в силу ≤ 60 с).
- Проверка после ротации: кнопка «Проверить» в админке
  (`POST /api/admin/llm/providers/{id}/test`) — зелёная.

## 4. Отчётность агентов

- В отчётах и протоколах верификации приводятся только: `has_api_key`,
  `key_last4`, `provider_id`, имя модели, latency, usage.
- Команды в протоколах приводятся с маскированными значениями
  (например, `Authorization: Bearer ***`).
