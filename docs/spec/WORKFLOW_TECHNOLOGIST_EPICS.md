# ProcessMap — Workflow для технолога: эпики и декомпозиция

> Основание: «Workflow для технолога в ProcessMap (доработанная версия)», ред. 2.
> Декомпозиция покрывает MVP детально; v1 и v2 — на уровне эпиков
> (детализация — после апрува MVP).

---

## 0. Протокол апрува эпиков (обязателен для агента)

Эпик считается закрытым **только после явного апрува пользователя**.
Агент не имеет права закрывать эпик по собственному решению и не имеет
права начинать следующий эпик до апрува предыдущего, если между ними
есть зависимость.

Для получения апрува агент обязан:

1. **Предъявить артефакты**, перечисленные в разделе «Артефакты для
   апрува» эпика: работающий фрагмент (демо/скрин/видео сценария),
   результаты тестов, ссылки на PR/коммиты, обновлённую документацию.
2. **Пройти чек-лист приёмки** эпика: явно перечислить каждый критерий
   и отметить статус (✅ выполнено / ❌ не выполнено / ⚠️ выполнено
   с оговоркой — с описанием оговорки). Каждый пункт подтверждается
   артефактом, а не декларацией.
3. **Продемонстрировать сквозной сценарий эпика** (демо-сценарий указан
   в каждом эпике) — не отдельные функции, а именно сценарий целиком.
4. **Зафиксировать открытые вопросы и отклонения**: всё, что сделано
   не по спецификации, должно быть перечислено явно.
5. **Запросить апрув** сообщением вида:

   > Эпик E{N} «{название}» готов к приёмке.
   > Чек-лист: {статусы по критериям}.
   > Артефакты: {ссылки}.
   > Демо-сценарий: {описание/запись}.
   > Отклонения: {список или «нет»}.
   > Прошу апрув на закрытие эпика.

6. Дождаться ответа пользователя:
   - **Апрув** → эпик закрыт, переход к следующему.
   - **Апрув с замечаниями** → замечания фиксируются как отдельные
     задачи (в backlog или следующий эпик — решает пользователь),
     эпик закрывается.
   - **Реджект** → эпик возвращается в работу, агент исправляет
     указанные пункты и повторяет запрос апрува. Повторный запрос
     содержит diff: что изменилось с прошлой итерации.

Запрещено: закрывать эпик «частично» без согласования; переносить
критерии приёмки в следующие эпики молча; считать молчание апрувом.

## 1. Карта эпиков MVP

```
E1 Инфраструктура и ролевая модель
   └─→ E2 Operation Catalog и словари (read)
        └─→ E3 Импорт BPMN → UI-модель
             └─→ E4 Конструктор процесса
                  └─→ E5 Recipe
                       └─→ E6 Dry-run валидация + pre-check
                            └─→ E7 Публикация и версионирование
                                 └─→ E8 Аудит-лог
                                      └─→ E9 Пилотный контур
```

Зависимости жёсткие по цепочке; E8 (аудит) технически можно начинать
параллельно с E7, но апрув E8 возможен только после апрува E7.

---

## Эпик E1. Инфраструктура и ролевая модель

**Цель:** каркас приложения, в котором аналитик и технолог работают
в общем редакторе с разными наборами функций.

**Задачи:**
- E1.1. Поднять структуру проекта: фронтенд редактора, backend
  (Process Template Service), Workflow Database (миграции).
- E1.2. Модель пользователей и ролей: `analyst`, `technologist`, `admin`.
- E1.3. Ролевая модель в UI: технологу скрыты функции аналитика
  (редактирование Operation Catalog, словарей, импорт BPMN, XML).
- E1.4. Базовые таблицы: `process_template`, `recipe`, `process_entity`,
  `operation_catalog`, `quality_policy`, `sku_binding`, `audit_log`
  (схема — по доработанной версии, раздел 4.2).
- E1.5. Health-check, базовая обработка ошибок API, логирование запросов.

**Критерии приёмки:**
1. Пользователь с ролью `technologist` видит только свой набор функций;
   роль `analyst` — полный.
2. Все таблицы созданы миграциями, есть rollback.
3. API отдаёт 401/403 корректно по ролям (автотест).

**Артефакты для апрува:** скрин/видео переключения ролей, вывод миграций,
зелёные автотесты по ролям.

**Демо-сценарий:** логин под технологом и под аналитиком — видимые
различия интерфейса; попытка технолога вызвать «аналитический» эндпоинт
напрямую → 403.

## Эпик E2. Operation Catalog и словари (read)

**Цель:** технолог видит блоки операций и типы сущностей; аналитик может
завести данные (загрузкой, UI для каталога — не MVP).

**Задачи:**
- E2.1. Таблица `operation_catalog` + сидирование карточками словаря
  v0.3: `get_from_storage`, `move`, `open_container`, `open_equipment`,
  `close_equipment`, `set_equipment`, `start_equipment`, `wait`,
  `close_container`, `transfer`, `check`, `measure_temperature`,
  `publish_event` (parameter_schema, allowed_outputs, execution_contract,
  resource_requirements — по формату §8–9).
- E2.2. Словари типов: `equipment_types`, `container_types`,
  `zone_types`, `sku` (минимум: типы из процесса супов — microwave,
  container_opener, container_dispenser, transfer_station,
  container_closing_station, fridge_storage, food_container,
  serving_container, disposal_zone, packaging_zone + 2–3 тестовых SKU).
- E2.3. API: GET /api/operation-catalog, GET /api/operation-catalog/{code},
  GET /api/dictionaries/*.
- E2.4. UI: каталог блоков (список + карточка операции с человеко-
  читаемым execution_contract — «что уже проверяется внутри блока»).

**Критерии приёмки:**
1. Все 12 операций v0.3 доступны через API с полными карточками.
2. Карточка операции в UI показывает execution_contract в виде,
   понятном не-программисту (русские формулировки, не сырой JSON).
3. Словари содержат типы, достаточные для процесса супов.

**Артефакты для апрува:** скрин карточки `transfer` и
`measure_temperature`, JSON ответа API по одной операции.

**Демо-сценарий:** технолог открывает каталог, находит `transfer`,
читает, какие проверки уже включены в блок.

## Эпик E3. Импорт BPMN → UI-модель

**Цель:** существующий BPMN (TO BE супа от ИТМО) превращается в
UI-модель редактора с отчётом о несоответствиях v0.3.

**Задачи:**
- E3.1. BPMN-парсер: задачи, шлюзы, события, потоки, дорожки,
  camunda:properties → поля UI-модели (operation_code, params, outputs,
  recipe_params).
- E3.2. Маппинг ссылок задач на process_entities; автосоздание
  чернового справочника сущностей из импортируемой схемы.
- E3.3. Отчёт о несоответствиях: неизвестный operation_code, условия
  шлюзов не из allowed_outputs, незадекларированные ссылки, лишние
  поля (validator_profile_id и т.п. — с рекомендацией удалить).
- E3.4. API: POST /api/process-templates/import-bpmn (файл → UI-модель
  + отчёт).
- E3.5. UI: экран результата импорта (предпросмотр графа + список
  замечаний с навигацией к элементу).

**Критерии приёмки:**
1. Файл «TO BE разогрев супа (РТК, v0.3).bpmn» импортируется без
   потери узлов и потоков (35 узлов, 36 потоков), отчёт — 0 критичных
   несоответствий.
2. Исходный файл ИТМО (v0.2-стиль) импортируется с корректным отчётом:
   перечислены validator_profile_id, actor_kind, ${}-подстановки,
   неизвестные коды операций.
3. Отчёт кликабелен: переход к элементу схемы.

**Артефакты для апрува:** видео импорта обоих файлов, экспорт отчёта
(текст/JSON).

**Демо-сценарий:** аналитик импортирует BPMN v0.3 → чистый отчёт;
импортирует старый BPMN ИТМО → отчёт со списком несоответствий
и навигацией.

## Эпик E4. Конструктор процесса

**Цель:** технолог собирает/правит процесс из блоков каталога, объявляет
сущности — без XML и без ручного ввода ссылок.

**Задачи:**
- E4.1. Визуальный редактор графа: узлы-блоки из каталога, шлюзы,
  события; соединение потоками.
- E4.2. Добавление блока из каталога → автоподстановка parameter_schema;
  форма параметров блока (обязательные поля подсвечены).
- E4.3. Панель process_entities: создание сущности выбором типа из
  словаря; ссылка на сущность в параметрах блока — только выбором
  из списка (никакого свободного ввода).
- E4.4. CRUD шаблонов: создать из шаблона/клонировать/сохранить черновик
  (API из раздела 4.5).
- E4.5. Ограничения конструктора: нельзя ввести произвольное условие
  шлюза — только из allowed_outputs предшествующих операций; нельзя
  удалить сущность, на которую есть ссылки.

**Критерии приёмки:**
1. Процесс супов собирается из блоков с нуля ≤ 30 минут
   (проверить на живом пользователе-технологе).
2. Невозможно сохранить блок с незаполненными обязательными параметрами.
3. Невозможно создать условие шлюза не из allowed_outputs.
4. Все ссылки на сущности — только из справочника процесса.

**Артефакты для апрува:** видео сборки процесса из 5+ блоков, попытки
«сломать» правила (пустые параметры, невалидное условие, удаление
связанной сущности) — система отказывает.

**Демо-сценарий:** технолог клонирует импортированный процесс супов,
добавляет блок `check` после `transfer`, настраивает параметры выбором
из списков, сохраняет черновик.

## Эпик E5. Recipe

**Цель:** recipe как отдельная сущность: один шаблон — много SKU
с разными параметрами.

**Задачи:**
- E5.1. CRUD recipe (API /api/recipes): sku_id + template_id +
  template_version + parameters_json.
- E5.2. Форма параметров recipe: типы, диапазоны, единицы измерения
  (heat_time_sec: 10–600, target_temp_c: 60–100 и т.п. — диапазоны
  в словаре параметров).
- E5.3. Связь recipe ↔ блоки: поле `recipe_params` в блоках (напр.,
  `set_equipment`) ссылается на имена параметров recipe; UI подсвечивает
  параметры, приходящие из рецепта.
- E5.4. Клонирование recipe на новый SKU.
- E5.5. Проверка полноты: все `recipe_params`, упомянутые в шаблоне,
  должны быть заполнены в recipe.

**Критерии приёмки:**
1. На один шаблон «супы» заведено ≥ 2 recipe с разными heat_time_sec —
   без дублирования шаблона.
2. Нельзя сохранить recipe с параметром вне диапазона.
3. Нельзя опубликовать recipe, если шаблон требует параметр,
   отсутствующий в recipe.

**Артефакты для апрува:** скрин двух recipe на одном шаблоне, негативные
кейсы (диапазон, полнота).

**Демо-сценарий:** технолог создаёт recipe для «Том ям» (120 сек) и
«Борщ» (90 сек) на одном шаблоне, пытается ввести 1000 секунд —
отказ с понятным сообщением.

## Эпик E6. Dry-run валидация + pre-check реализуемости

**Цель:** двухступенчатая проверка до публикации: формат v0.3 (§15)
и исполнимость на целевых кухнях.

**Задачи:**
- E6.1. Validation Service: правила §15 (operation_code из каталога,
  параметры по схеме, ссылки объявлены, условия шлюзов из
  allowed_outputs, обязательные params для move/transfer, связность
  графа: достижимость от старта, пути к концу).
- E6.2. API: POST /api/process-templates/{id}/validate — структурированный
  список ошибок с привязкой к элементу.
- E6.3. Реестр конфигураций кухонь (MVP-вариант: таблица `kitchen`
  с типами оборудования; интеграция с Digital Twin/Asset Registry —
  v1+).
- E6.4. Pre-check: объединение resource_requirements операций шаблона
  vs типы оборудования целевых кухонь; режимы strict/warning
  (конфигурируемо).
- E6.5. UI: панель результатов валидации с навигацией к элементу.

**Критерии приёмки:**
1. Валидный процесс супов проходит dry-run без ошибок.
2. Каждое правило §15 имеет хотя бы один негативный тест-кейс.
3. Процесс с `measure_temperature` не проходит pre-check на кухне
   без средств измерения (в strict-режиме — блок, в warning —
   предупреждение).

**Артефакты для апрува:** набор негативных кейсов с результатами,
скрин панели валидации, конфиг strict/warning.

**Демо-сценарий:** технолог валидирует процесс → чисто; аналитик
ломает схему (удаляет обязательный param, добавляет невалидное
условие) → ошибки с навигацией; публикация на кухню без тепловизора —
предупреждение/блок по режиму.

## Эпик E7. Публикация и версионирование

**Цель:** публикация версии связки «шаблон + recipe», генерация BPMN-XML,
блокировка версий.

**Задачи:**
- E7.1. BPMN Generator: UI-модель → BPMN-XML (задачи с
  camunda:properties, шлюзы с conditionExpression, дорожки, DI-разметка
  для открытия в Camunda Modeler).
- E7.2. Publish flow: валидация → pre-check → генерация XML →
  версия (major.minor.patch) → статус published, блокировка
  редактирования.
- E7.3. API: POST /api/process-templates/{id}/publish,
  POST /api/recipes/{id}/publish.
- E7.4. Изменение опубликованного: только «создать новую версию»
  (копия в черновик).
- E7.5. Раунд-трип: сгенерированный XML открывается в Camunda Modeler
  и реимпортируется (E3) без потерь.

**Критерии приёмки:**
1. Опубликованная версия не редактируется; изменение = новая версия.
2. Сгенерированный BPMN-XML процесса супов открывается в Camunda
   Modeler и соответствует v0.3 (все задачи с operation_code,
   ссылки объявлены).
3. Раунд-трип XML → импорт → UI-модель без потери узлов/потоков.

**Артефакты для апрува:** сгенерированный .bpmn файл, скрин в Camunda
Modeler, скрин блокировки версии.

**Демо-сценарий:** технолог публикует «Супы v1.0.0» + recipe «Борщ v1»;
пытается править опубликованное — система предлагает новую версию;
файл открывается в Camunda Modeler.

## Эпик E8. Аудит-лог

**Цель:** ответ «кто, когда, что изменил» в один клик — обязателен
для параметров пищевой безопасности.

**Задачи:**
- E8.1. Запись событий в `audit_log`: create/update/publish/pilot_start/
  rollout/retire для template, recipe, binding, quality_policy —
  с diff_json (старое/новое значение полей).
- E8.2. API: GET /api/audit-log (фильтры по сущности/актору/периоду),
  GET /api/recipes/{id}/diff.
- E8.3. UI: журнал по сущности (вкладка «История»), человеко-читаемый
  diff параметров recipe («target_temp_c: 75 → 80, кто, когда»).
- E8.4. Журнал неизменяем: нет API на update/delete записей.

**Критерии приёмки:**
1. Изменение параметра recipe отражается в журнале с diff
   в течение секунды после сохранения.
2. По любой опубликованной версии видно автора, дату и полный diff
   от предыдущей версии.
3. Записи журнала нельзя изменить через API.

**Артефакты для апрува:** скрин вкладки «История» с diff
target_temp_c, результат попытки изменить запись через API.

**Демо-сценарий:** технолог меняет heat_time_sec 90 → 100, публикует
новую версию; в истории видны обе записи и diff; вопрос «кто изменил
температуру» отвечается в один клик.

---

## Эпик E9. Пилотный контур

**Цель:** привязка recipe к кухням через пилот с критерием выхода;
раскатка без новых версий процесса.

**Задачи:**
- E9.1. Таблица `sku_binding` + статусная модель: draft → pilot →
  active → retired.
- E9.2. API rollout-группы: создание привязки, start-pilot
  (pilot_kitchen_id + pilot_exit_criteria_json), pilot-metrics, rollout.
- E9.3. Критерий выхода: конструктор условий (число заказов, критичные
  ошибки, доля брака) с валидацией.
- E9.4. Сбор метрик пилота (MVP: ручной ввод/заглушка-агрегатор
  с API-контрактом под САУ РТК; интеграция — v1+).
- E9.5. UI: карточка пилота (прогресс к критерию, кнопка раскатки —
  активна только при выполнении критерия), расширение kitchen_ids
  с записью в аудит.

**Критерии приёмки:**
1. Пилот создаётся на 1 кухню с критерием выхода; статусная модель
   соблюдается (нельзя rollout до выполнения критерия).
2. Раскатка расширяет kitchen_ids без создания новой версии шаблона/recipe
   и пишется в аудит.
3. Метрики пилота доступны через API-контракт (с заглушкой данных).

**Артефакты для апрува:** скрин карточки пилота с прогрессом, отказ
раскатки при невыполненном критерии, запись rollout в аудит-логе.

**Демо-сценарий:** технолог создаёт пилот «Борщ v1 → кухня №1»,
критерий: 20 заказов, 0 критичных ошибок; метрики доходят до 20 —
кнопка раскатки активируется; раскатка на кухни №2–3 фиксируется
в истории.

## 2. Критерии приёмки MVP целиком (финальный апрув)

После апрува E9 агент запрашивает **финальный апрув MVP**:

1. Сквозной сценарий от импорта BPMN до раскатки выполняется без
   ручных правок БД/XML (запись скринкаста целиком).
2. На одном шаблоне «супы» — ≥ 2 recipe, ≥ 1 опубликованная версия,
   ≥ 1 завершённый пилот.
3. Все критерии E1–E9 имеют статус ✅ (или ⚠️ с оговорками,
   принятыми пользователем).
