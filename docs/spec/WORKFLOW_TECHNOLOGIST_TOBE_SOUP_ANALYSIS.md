# Анализ и доработка процесса TO BE разогрева супа

**Входные материалы:** BPMN AS IS (ручной процесс: сотрудник / оборудование / программа сборки), BPMN TO BE от института робототехники (ИТМО, дорожки «манипуляторы / оператор / оборудование»), документ «Черновик формата описания операций технологического процесса, v0.3» (договорённость между аналитиком, Оркестратором, Scheduler, САУ РТК, Digital Twin и СТЗ).

**Результат:** доработанная схема `TO BE разогрев супа (РТК, v0.3).bpmn` — открывается в Camunda Modeler, приведена к формату v0.3 и пригодна как основа для настройки технологами.

---

## 1. Главный вывод

Схема ИТМО — хорошая основа по **макрологике** (правильный скелет: хранение → вскрытие → СВЧ → перетарка → закрытие → зона упаковки; удачная параллельная выдача тары покупателя во время нагрева; сквозные `*_ref`; различие исходной тары и тары покупателя; идея scheduler-маппинга оборудования).

Но по форме она написана в терминах **прошлой редакции формата (v0.2)** и почти по каждому пункту расходится с v0.3 — тем самым документом, по которому её дальше будут настраивать технологи. Плюс в потоке есть **логические ошибки**, часть из которых критична для безопасности продукта (потерян контроль температуры ≥ 75 °C и цикл догрева, потеряна проверка дефекта тары, нет ожидания окончания нагрева — робот открывает СВЧ сразу после запуска).

Доработка = сохранить скелет ИТМО, перевести разметку на v0.3, вернуть процессно значимые проверки из AS IS, починить ошибки потока.

---

## 2. Что в схеме ИТМО сделано хорошо (сохранено)

| Приём | Почему важно |
|---|---|
| Сквозные условные ссылки `container_1/container_2`, refs на оборудование | Совпадает с идеологией v0.3: условные ссылки вместо физических ID |
| Различие `source_container_state=legacy` / `target_container_state=new` | Правильная мысль: старая тара — отход после перелива, тара покупателя — новая |
| Параллельная ветка «выдать контейнер-2» во время нагрева | Экономит цикл, оставлена в доработанной схеме |
| Идея «equipment_ref назначает scheduler», «recipe_context задаёт режим» | Прямо соответствует v0.3 (динамический runtime-маппинг, рецептурные параметры) |
| Перенос всей упаковки за пределы схемы блюда | Соответствует §16 формата (упаковка — общий процесс) |

## 3. Несоответствия формату v0.3 (и как исправлено)

| # | Что в схеме ИТМО | Что требует v0.3 | Исправление в новой схеме |
|---|---|---|---|
| 1 | `validator_profile_id` в почти каждой задаче (в одном месте — с лишним пробелом) | Валидационные профили полностью исключены (комментарий №14) | Удалены; проверки — в Operation Catalog / Quality Policy |
| 2 | `actor_kind=robot/equipment` | `actor_kind` исключён (№6, №17); исполнитель определяется каталогом и конфигурацией кухни | Удалён; дорожки оставлены только как визуальная группировка |
| 3 | `operation_id` заполнен вручную (`op_move_to_sealer` и т.п.), причём `op_open_bin` продублирован на двух задачах | `operation_id` — служебный, генерируется Configurator/Loader, аналитик не заполняет (№5) | Удалены; уникальность восстановится автоматически |
| 4 | Подстановки `${recipe_context.dish_sku_id}`, `${recipe_context.power_mode}` | Шаблонные подстановки исключены (№18); значения подставляются при создании process_instance | Введено поле `recipe_params` со списком имён параметров рецепта (без `${}`) |
| 5 | Коды операций не из словаря: `move_object`, `transfer_contents`, `configure_equipment`, `seal_container`, `grasp_object` | Словарь v0.3: `move`, `transfer`, `set_equipment`, `close_container`, … | Все задачи переведены на коды словаря |
| 6 | `grasp_object` — «Поднести контейнер-1 к устройству перетаривания» | «Взять — переместить — положить» — стандартная декомпозиция ниже схемы (§2, §9) | Убрана; слита в `move` |
| 7 | `seal_container` + `seal_method=close_lid` | Метод закрытия не указывается в BPMN (№12): `close_container`, метод — по типу тары | `close_container` без метода |
| 8 | `dish_sku_id` в `transfer` | Удалён из минимальных параметров transfer (№21) | Убран |
| 9 | Заглушки-дефисы: `purpose="-"`, `validator_profile_id="-"`, `equipment_type_id="-"` | Опциональные поля не записываются; явный null/заглушки не используются (№7, §2) | Поля отсутствуют |
| 10 | Псевдо-значения: `equipment_ref="scheduler_or_fixed_runtime"`, `equipment_ref="required_runtime"`, `source_container_ref="required"` | Ссылки должны быть объявлены в справочнике сущностей; scheduler-маппинг — runtime, а не значение в схеме | Настоящие условные ссылки + текстовая аннотация про runtime-маппинг |
| 11 | «Выдать контейнер-1 из холодильника» и «Выдать контейнер-2…» — без `operation_code` вообще | Каждая исполняемая задача должна иметь `operation_code` (§15) | `get_from_storage` с `item_ref` + `target_ref` |
| 12 | Справочник сущностей и recipe_context — только в свободных текстовых аннотациях | Формализованные `process_entities` и `recipe_context` (§5) | Структурированная аннотация-справочник с типами (`microwave`, `transfer_station`, `disposal_zone`…) + список параметров рецепта |
| 13 | Ручные `manualTask` для операций робота/оборудования | UserTask/ManualTask не входят в базовый профиль v0.3 (№6); Task = макрооперация | Все операции — нейтральный `Task` |
| 14 | Пул назван «AS IS Супы» | — | Переименован в «TO BE Супы (РТК) — формат v0.3» |

## 4. Логические ошибки потока (исправлены)

1. **Нет ожидания нагрева — критично.** После «Запустить СВЧ-1» процесс через параллельный шлюз сразу идёт в «Открыть СВЧ-1»: робот откроет печь мгновенно после старта. В v0.3 для этого есть операция `wait` / событие ожидания. → Добавлено промежуточное событие «Нагрев завершён (heating_finished)».
2. **Потерян контроль температуры ≥ 75 °C и цикл догрева — критично (пищевая безопасность).** В AS IS это явная проверка (пар/масляные пятна → термощуп → при необходимости повторный разогрев). По v0.3 это классическая *рецептурная проверка*, которая обязана быть в BPMN (`measure_temperature` + Gateway — прямой пример из §10–11 формата). → Добавлены `measure_temperature` с outputs `temperature_ok` и шлюз «Температура ≥ 75 °C?» с петлёй догрева (закрыть → запустить → дождаться → измерить снова).
3. **Потеряна проверка дефекта тары.** В AS IS после нагрева — проверка «протечка/деформация?» с подпроцессом «Дефект тары» и рестартом. → Добавлена `check` (`check_code=container_integrity`) со шлюзом: дефект → утилизация → `RESTART_SOUP`.
4. **RESTART_SOUP — мёртвая ветка.** В схеме ИТМО есть link-catch RESTART_SOUP, но нет ни одного link-throw (throw остался в файле AS IS) — рестарт физически не может сработать. → Добавлен парный throw в ветке дефекта; петля замкнута.
5. **Урна открывается после того, как тара в неё «перенесена», и дважды.** Последовательность «Перенести контейнер-1 в урну-1 → Открыть урну-1», плюс две разные задачи «Открыть урну-1» с одним `operation_id`. → По v0.3 открытие урны вообще не моделируется (это часть execution_contract перемещения в зону утилизации): оставлен один `move` в `waste_zone_1`, порядковая ошибка устранена вместе с дублем.
6. **Несовпадение имени и параметров.** «Перенести контейнер-2 в устройство-перетаривания-1» имеет `target_ref=assembly_zone_1`. → Цель приведена к `transfer_station_1`, все ссылки объявлены в справочнике.
7. **Старт «по звуковому сигналу».** None-старт «Заказ на суп» → ожидание message «Звуковой сигнал о новом заказе» — артефакт ручной эпохи: в РТК экземпляр процесса создаёт Workflow Loader по заказу. → Заменено на message start event «Заказ на суп (order_created)».
8. **Два шлюза с именем «Решение 1»** (один exclusive, один parallel) и «Решение 2» — копипаст, сбивает технологов. → Шлюзы либо безымянные (слияния/параллельность), либо названы по вопросу («Температура ≥ 75 °C?», «Контейнер цел?»); на исходящих потоках — формальные условия по outputs.
9. **Пустая дорожка «Работа оператора».** → Удалена (ручной контур — открытый вопрос №26 формата, в схеме блюда ему не место).
10. **Финиш без события для упаковки.** §16: схема блюда завершается состоянием «контейнер передан в зону упаковки» **или** событием `ready_for_packaging`. → Добавлены оба: `move` в `packaging_zone_1` + `publish_event(ready_for_packaging)` — общий процесс упаковки сможет стартовать событием.

## 5. Что осознанно НЕ перенесено из AS IS (и почему это правильно)

| Элемент AS IS | Решение | Основание |
|---|---|---|
| Ветвление «тара с крышкой / с плёнкой», нож | Не моделируется: `open_container` один, метод вскрытия выбирается по `source_container_type` из recipe_context | v0.3: способ исполнения — ниже схемы; ветка по типу тары не меняет маршрут |
| Педаль мусорки, «руками крышку не трогать», переполнение | Не моделируется; зона утилизации + execution_contract | Человеческие ограничения; в РТК решается оснасткой/конфигурацией |
| Пролив/капли при переливе, протирание салфеткой | Не отдельная задача; контроль качества перетарки — execution_contract `transfer` + Quality Policy (L4) | §10, §13: стандартный результат операции в схеме не рисуется |
| «Убедиться, что суп плотно закрыт», переукупорка | Часть execution_contract `close_container` + локальное восстановление | §10 |
| Топпинги, приборы, пакет, этикетки, тепловой шкаф, кнопка «заказ готов» | Общий процесс упаковки заказа, стартует от `ready_for_packaging` | §16 |
| Мойка поверхностей | Отдельный сервисный процесс, не часть схемы блюда | Фоновое состояние среды / maintenance (§10) |
| «Взять разогретый суп», «перенести над контейнером» как отдельные захваты | Стандартная декомпозиция `move`/`transfer` | §2 |

При этом всё **процессно значимое** из AS IS сохранено: контроль температуры, дефект тары с рестартом, утилизация исходной тары, различение тары legacy/new, передача в упаковку.

## 6. Доработанный процесс (файл `TO BE разогрев супа (РТК, v0.3).bpmn`)

**Поток (happy path):**

1. `message start`: Заказ на суп → (точка входа рестарта)
2. `get_from_storage`: контейнер-1 из хранения (`storage_1`)
3. `move` → в устройство вскрытия (`opening_equipment_1`)
4. `open_container`: вскрыть контейнер-1 (метод — по типу тары)
5. `open_equipment`: открыть СВЧ → `move`: контейнер-1 в СВЧ → `close_equipment`
6. `set_equipment`: режим нагрева (`heating_power`, `heat_time_sec` из рецепта)
7. **Параллельно:** (а) `start_equipment` → ожидание «Нагрев завершён»; (б) `get_from_storage` контейнер-2 → `move` в станцию перетаривания
8. `open_equipment` СВЧ → `measure_temperature` → **шлюз «≥ 75 °C?»** (нет → петля догрева)
9. `check` целостности контейнера-1 → **шлюз** (дефект → утилизация → `RESTART_SOUP` → новый цикл с п.1)
10. `move` контейнер-1 в станцию перетаривания → `close_equipment` СВЧ
11. `transfer`: перетарить суп контейнер-1 → контейнер-2
12. `move` контейнер-1 в зону утилизации
13. `move` контейнер-2 в станцию закрытия → `close_container` (метод — по типу тары)
14. `move` контейнер-2 в зону упаковки → `publish_event(ready_for_packaging)` → end

**Статистика:** 35 узлов, 36 потоков; все задачи — с `operation_code` из каталога; схема проверена на связность (каждый узел достижим, все пути ведут к завершению или к рестарту).

## 7. Что останется настроить технологам

1. **recipe_context** на каждый SKU супа: `heating_power`, `heat_time_sec`, `target_temp_c`, `portion_qty`, `source_container_type` (+ параметры режима догрева).
2. **Словари типов**: `food_container`, `serving_container`, `microwave`, `container_opener`, `container_dispenser`, `transfer_station`, `container_closing_station`, `fridge_storage`, `disposal_zone`, `packaging_zone` (открытый вопрос №3 формата — утвердить словари и версионирование).
3. **Карточки Operation Catalog** для использованных кодов: особенно `transfer` (допустимые захваты/оснастка под горячую тару, критерии качества перетарки), `close_container` (какие методы закрытия доступны под каждый `container_type`), `measure_temperature` (доступные методы измерения).
4. **Quality Policy**: сколько догревов допустимо, прежде чем вернуть процессную ошибку (сейчас петля догрева потенциально бесконечна — это осознанно оставлено политике, см. открытый вопрос №28); что делать при повторном дефекте тары.
5. **Runtime-маппинг** условных ссылок на физические ресурсы конкретной кухни — на стороне Scheduler, схему не трогаем.
6. **Интеграционный слой**: отображение канонических параметров (`heating_power` и пр.) на OPC UA-теги конкретных СВЧ.

## 8. Открытые вопросы (к обсуждению с ИТМО и технологами)

1. **Петля догрева**: ограничивать ли число повторов на схеме (счётчик + ветка эскалации) или отдать в Quality Policy? Рекомендация — политика, схему не усложняем.
2. **Где измерять температуру**: в исходной таре внутри открытой СВЧ (как заложено) или после перетарки в таре покупателя? Второе точнее для клиента, но догревать тару покупателя может быть недопустимо — зависит от оснастки и СанПиН-логики.
3. **Точка проверки целостности**: сейчас — после нагрева (как в AS IS). СТЗ может дёшево проверять тару и при выдаче из хранения — тогда дефект отбраковывается до расхода энергии на нагрев. Стоит добавить второй `check` при росте доли брака на входе.
4. **Компоновка**: в AS IS «контейнер клиента всегда в зоне СВЧ, перемещений по кухне нет». В TO BE тара покупателя едет в отдельную станцию перетаривания — подтвердить, что компоновка РТК это допускает (или переливать прямо в зоне СВЧ, тогда `transfer_station_1` убирается из маршрута контейнера-2).
5. **Ручной контур** (отладка, нештатные ситуации) — открытый вопрос №26 формата; пока в схему не включён.
6. **Событие завершения нагрева**: сообщение от оборудования (`heating_finished`) или таймер по `heat_time_sec`? Заложено событие; если СВЧ его не отдаёт — заменить на `wait(duration)` без изменения топологии.
