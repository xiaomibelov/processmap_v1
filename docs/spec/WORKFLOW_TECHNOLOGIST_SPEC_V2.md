# Workflow для технолога в ProcessMap — доработанная версия

> Редакция 2. Доработано по замечаниям: добавлено обоснование точки входа,
> поток импорта BPMN → UI-модель, сущность recipe, пилотный этап, аудит-лог,
> pre-check реализуемости на публикации, варианты размещения Operation Catalog.
> Разделы 1, 3 (MoSCoW обновлён), 4 (модель данных и API обновлены) изменены,
> остальное сохранено с уточнениями.

---

## 1. Резюме решения

Workflow технолога живёт в **«режиме технолога» внутри общего редактора
ProcessMap**, а не в отдельном приложении. Режим — это ролевая модель +
упрощённый UI поверх той же кодовой базы и той же промежуточной UI-модели
процесса. Технолог никогда не видит BPMN-XML и не редактирует его;
UI-модель транслируется в исполняемую BPMN-схему при публикации.

Жизненный цикл: черновик → валидация → публикация → **пилот** →
эксплуатация → изменение/отзыв. Технолог отвечает за содержание процесса
(рецепт, параметры, проверки), система — за исполняемость и валидность.

Границы ответственности:

- **Аналитик** создаёт Operation Catalog, словари типов, формат v0.3
  и исходные шаблоны процессов (в т.ч. импортом существующих BPMN)
- **Технолог** собирает процесс из блоков, настраивает recipe_context,
  проверки, Quality Policy, публикует версии и ведёт пилоты
- **Scheduler** мапит условные ссылки на физические ресурсы кухни
  (runtime-mapping)
- **САУ РТК** исполняет процесс, отчитывается об ошибках

### 1.1. Обоснование точки входа (добавлено)

Рассматривались три варианта:

| Критерий | Режим в общем редакторе ✅ | Отдельный кабинет | Набор отдельных инструментов |
|---|---|---|---|
| Стоимость разработки | Низкая: один фронтенд, одна UI-модель | Высокая: второй фронтенд | Средняя, но фрагментированный UX |
| Консистентность модели | Гарантирована: аналитик и технолог работают с одной моделью | Риск расхождения UI-моделей | Высокий риск расхождения |
| Один источник правды для BPMN-генерации | Да | Нужна синхронизация | Нужна синхронизация |
| Скорость внедрения новых правил формата | Мгновенно для обеих ролей | Дублирование изменений | Дублирование изменений |
| UX для технолога | Упрощается ролью (скрытие функций аналитика) | Можно сделать «чище», но ценой дублирования | Плохой: переключения между инструментами |

**Решение: режим в общем редакторе.** Ключевой аргумент — единая UI-модель
и единый генератор BPMN: любое изменение формата v0.3 подхватывается один
раз, а не в двух приложениях. Отдельный кабинет имеет смысл пересмотреть
только если аудитории аналитиков и технологов разойдутся радикально
(десятки технологов без доступа к аналитическим функциям) — это
кандидат в v2+.

## 2. Этапы жизненного цикла с ролями

| Этап | Технолог | Система | Блокировки |
|---|---|---|---|
| **Черновик** | Создаёт/клонирует процесс из шаблона, заполняет recipe, объявляет сущности | Генерирует UI-модель (в т.ч. импортом из BPMN), валидирует типы и диапазоны | Нет |
| **Валидация** | Проверяет схему (dry-run), смотрит execution_contract | Проверяет по правилам v0.3 (§15), покрытие проверок, валидность условий | Нет |
| **Симуляция** (v2) | Запускает имитацию на Digital Twin | Эмулирует выполнение, показывает поток и ошибки | Нет |
| **Публикация** | Публикует версию, привязывает к SKU и кухням | Версионирует шаблон и recipe, **pre-check реализуемости на целевых кухнях**, блокирует редактирование опубликованной версии | ✅ Версия заблокирована |
| **Пилот** | Назначает пилот на 1 кухню, наблюдает прогон реальных заказов, принимает решение о раскатке | Ведёт метрики пилота (число заказов, process_visible_errors, брак), показывает критерий выхода | ✅ Раскатка только после выполнения критерия выхода |
| **Эксплуатация** | Мониторит ошибки, анализирует брак | Показывает process_visible_errors, метрики, логи | ❌ Нет редактирования |
| **Изменение/отзыв** | Создаёт новую версию на основе текущей, отзывает устаревшую | Сравнивает версии (diff параметров и схемы), уведомляет о конфликтах, деактивирует старые | ✅ Только через новую версию |

### 2.1. Пилотный этап (добавлено)

Между публикацией и эксплуатацией — обязательный пилот для процессов,
влияющих на пищевую безопасность:

- `sku_binding` создаётся с одним `kitchen_id` (пилотная кухня).
- Критерий выхода задаётся при старте пилота, например: **≥ 20 заказов,
  0 критичных process_visible_errors, доля брака < порога**.
- После выполнения критерия технолог расширяет `kitchen_ids` в привязке
  (без новой версии шаблона — это операция раскатки, а не изменение
  процесса) или создаёт новую версию, если пилот выявил проблемы.
- Каждое расширение привязки фиксируется в аудит-логе.

## 3. UI-потоки технолога (MoSCoW, обновлён)

### Must Have (MVP)

| Поток | Описание | Зависимости |
|---|---|---|
| **Импорт BPMN → UI-модель** | Аналитик импортирует существующий BPMN (напр., TO BE супа от ИТМО), система строит UI-модель, мапит camunda:properties на поля операций, выдаёт список несоответствий формату v0.3 | BPMN-парсер, валидатор формата |
| Создание/клонирование процесса из шаблона | Сборка из блоков Operation Catalog, не рисование BPMN с нуля | Operation Catalog, словари типов |
| Управление recipe | Форма параметров на SKU с валидацией типов и диапазонов; один шаблон — много recipe | Словари SKU, типы параметров |
| Объявление process_entities | Выбор из словарей типов, без ручного ввода ссылок | Словари типов оборудования/контейнеров |
| Просмотр execution_contract | Какие generic-проверки уже включены в блок | Operation Catalog |
| Dry-run валидация | Проверка по правилам v0.3 до публикации | Валидатор формата |
| Публикация версии | Версионирование + **pre-check реализуемости на целевых кухнях** (см. 4.3) | Workflow Database, конфигурации кухонь |
| **Аудит-лог** | Журнал: кто, когда, что изменил (параметры recipe, схема, привязки); diff версий recipe | Версионирование |
| **Пилот** | Создание пилотной привязки на 1 кухню, критерий выхода, метрики прогона | Метрики САУ РТК |

### Should Have (v1)

| Поток | Описание | Зависимости |
|---|---|---|
| Настройка рецептурных проверок и шлюзов | Только из allowed_outputs операций, защита от невалидных условий | Operation Catalog |
| Настройка Quality Policy | Лимиты повторов, эскалации | Execution Policy |
| Управление изменениями | Новая версия при изменении состава оборудования кухни | Версионирование, Scheduler |
| Сравнение версий | Визуальный diff схемы и параметров | Аудит-лог |

### Could Have (v2)

| Поток | Описание | Зависимости |
|---|---|---|
| Симуляция на Digital Twin | Имитация выполнения до публикации | Digital Twin API |
| Обработка process_visible_errors | Анализ ошибок, корректирующие действия | САУ РТК, логи |
| Анализ брака | Статистика, причины, корректировка процесса | Метрики, история |
| Отдельный кабинет технолога | Выделенное приложение при масштабировании аудитории | Переиспользование UI-модели |

### Won't Have (не для технолога)

- Редактирование BPMN-XML или camunda:properties
- Runtime-маппинг на физические ресурсы (это Scheduler)
- Конфигурация OPC UA-тегов (это интеграционный слой)

## 4. Архитектурное решение

### 4.1. Компоненты

```
[Аналитик / Технолог] → [ProcessMap Editor (общий фронтенд, ролевая модель)]
                               ↓
                     [Process Template Service]
                               ↓
       [Operation Catalog] [Dictionary Service] [BPMN Importer] [BPMN Generator]
                               ↓
                     [Validation Service] → [Digital Twin] (v2)
                               ↓
                     [Workflow Database]
                               ↓
              [Version Control Service] [Audit Log Service]
                               ↓
                     [Rollout Service] (пилоты, привязки к кухням)
```

### 4.2. Модель данных (обновлена)

```sql
process_template (
  id, name, description, version, status,          -- status: draft|published|pilot|active|retired
  bpmn_xml, ui_model, created_by, created_at,
  published_at, published_by
)

recipe (                                          -- ОТДЕЛЬНАЯ сущность (была recipe_context)
  id, sku_id, process_template_id,                -- N recipe на 1 шаблон: один «супы» — много SKU
  template_version,                               -- recipe привязан к конкретной версии шаблона
  parameters_json,                                -- heating_power, heat_time_sec, target_temp_c...
  status, created_by, created_at, published_at
)

process_entity (
  id, process_template_id, name,
  type_id, type_category, attributes_json
)

operation_catalog (
  id, operation_code, name, description,
  parameter_schema_json, allowed_outputs_json,
  execution_contract_json, resource_requirements_json
)

quality_policy (
  id, process_template_id,
  retry_limits_json, escalation_rules_json
)

sku_binding (
  id, recipe_id,                                  -- привязка recipe (а не шаблона) к кухням
  kitchen_ids, pilot_kitchen_id,
  pilot_exit_criteria_json,                       -- критерий выхода из пилота
  valid_from, valid_to, status                    -- status: pilot|active|retired
)

audit_log (                                       -- ДОБАВЛЕНО
  id, entity_type, entity_id,                     -- template | recipe | binding | quality_policy
  action,                                         -- create|update|publish|pilot_start|rollout|retire
  actor_id, actor_role, timestamp,
  diff_json                                       -- что именно изменилось (параметры, схема, кухни)
)
```

Ключевые изменения модели:

1. **recipe отделён от шаблона.** Один шаблон «супы» обслуживает N SKU
   с разными `heat_time_sec`/`heating_power`. В первой редакции
   recipe_context содержал `sku_id` внутри шаблона, что вело к
   дублированию шаблонов на каждый SKU.
2. **Публикация версионирует связку** «шаблон-версия + recipe-версия»,
   привязка к кухням — отдельной операцией (rollout), не создающей
   новых версий процесса.
3. **audit_log** — обязателен с MVP: параметры вроде `target_temp_c`
   относятся к пищевой безопасности, вопрос «кто и когда изменил»
   должен отвечаться в один клик.

### 4.3. Pre-check реализуемости при публикации (добавлено)

Dry-run проверяет схему синтаксически (§15), но не отвечает на вопрос
«может ли хоть одна целевая кухня это исполнить». Поэтому публикация —
двухступенчатая:

1. **Валидация формата** (правила §15): operation_code из каталога,
   параметры по parameter_schema, ссылки объявлены в process_entities,
   условия шлюзов — только из allowed_outputs.
2. **Pre-check реализуемости**: для каждого `kitchen_id` в привязке
   проверяется, что объединение resource_requirements всех операций
   покрывается типами оборудования, доступными на кухне. Например, если
   `measure_temperature` требует capability «измерение температуры», а на
   кухне нет ни тепловизора, ни щупа — публикация на эту кухню
   блокируется с понятной ошибкой (вместо runtime-ошибки
   `capability_unavailable` на первом же заказе).

Источник данных о конфигурации кухонь — ресурсный контур (Digital Twin /
Asset Registry). Если реестр кухонь ещё не заполнен, pre-check работает
в режиме предупреждения, а не блокировки (конфигурируется).

### 4.4. Варианты размещения Operation Catalog (добавлено)

Открытый вопрос №27 формата. Варианты с критериями выбора:

| Вариант | Когда выбирать | Плюсы | Минусы |
|---|---|---|---|
| **Реляционная БД** (таблица operation_catalog, как в модели выше) | Редактируют аналитики через UI; нужны запросы, связи с шаблонами | Простой API, транзакции, FK на шаблоны | Нет истории изменений «из коробки» (нужен аудит-лог), изменения не проходят code review |
| **Git-репозиторий** (YAML-карточки, CI-валидация) | Изменения редки и критичны; нужен code review на execution_contract | История, review, откат, CI-проверки схем | Нужен импорт в БД для runtime-запросов; неудобен не-разработчикам |
| **Гибрид: git — источник правды, БД — read-модель** | Каталог критичен для безопасности исполнения И при этом запрашивается в runtime | Review + история + быстрые запросы | Сложнее инфраструктура (pipeline git → БД) |

**Рекомендация: гибрид.** execution_contract и process_visible_errors —
это контракт безопасного исполнения; их изменение без review недопустимо.
Git даёт историю и ревью, БД — быстрый доступ для Кабинета технолога и
Workflow. На MVP допустимо начать с БД + аудит-лог, заложив миграцию
на гибрид в v1. Те же соображения применимы к словарям типов
(equipment_type, container_type...).

### 4.5. API (обновлён)

Process Templates:
- GET /api/process-templates — список шаблонов
- POST /api/process-templates — создать/клонировать
- **POST /api/process-templates/import-bpmn — импорт BPMN → UI-модель
  (возвращает UI-модель + отчёт о несоответствиях v0.3)**
- GET /api/process-templates/{id} — получить шаблон
- PUT /api/process-templates/{id} — обновить черновик
- POST /api/process-templates/{id}/publish — опубликовать версию
  (запускает валидацию §15 + pre-check реализуемости)
- POST /api/process-templates/{id}/validate — dry-run валидация

Recipe:
- GET /api/recipes?template_id=… — список recipe шаблона
- POST /api/recipes — создать recipe (sku_id + шаблон + параметры)
- PUT /api/recipes/{id} — обновить черновик recipe
- POST /api/recipes/{id}/publish — публикация версии recipe

Process Entities:
- GET /api/process-entities/{template_id} — список сущностей
- POST /api/process-entities/{template_id} — добавить сущность
- DELETE /api/process-entities/{id} — удалить сущность

Operation Catalog:
- GET /api/operation-catalog — список операций
- GET /api/operation-catalog/{code} — карточка операции

Dictionaries:
- GET /api/dictionaries/equipment-types
- GET /api/dictionaries/container-types
- GET /api/dictionaries/sku

Rollout (пилоты и привязки):
- POST /api/sku-bindings — создать привязку (recipe → кухни, пилот)
- POST /api/sku-bindings/{id}/start-pilot — старт пилота с критерием выхода
- GET /api/sku-bindings/{id}/pilot-metrics — метрики пилота
- POST /api/sku-bindings/{id}/rollout — расширение на кухни после пилота

Audit:
- GET /api/audit-log?entity_type=…&entity_id=… — журнал изменений
- GET /api/recipes/{id}/diff?from=…&to=… — diff версий recipe

### 4.6. Версионирование

- process_template: каждая публикация — новая версия (major.minor.patch)
- recipe: привязан к версии шаблона, не редактируется после публикации;
  изменение параметров = новая версия recipe
- BPMN-XML: генерируется из UI-модели при публикации, сохраняется
  как артефакт версии
- Раскатка на новые кухни НЕ создаёт новую версию (это операция rollout,
  фиксируется в аудит-логе)

## 5. Риски и компромиссы

| Риск | Компромисс | Митигация |
|---|---|---|
| Свобода редактирования BPMN vs жёсткий конструктор | Конструктор из блоков с ограниченной гибкостью | Разрешить добавление только allowed_outputs, запретить произвольные условия |
| Generic-проверки в блоках vs кастомные | execution_contract для generic, allowed_outputs для кастомных | Показывать технологу, что уже включено, чтобы не дублировать |
| Точность симуляции vs скорость разработки | MVP: dry-run + pre-check реализуемости, v2: Digital Twin | Начать с валидации, симуляцию добавить позже |
| Сложность версионирования vs простота | Скрыть версии за UI, показывать «текущую» и «новую» | Автоматическое создание версий при изменении |
| Расхождение импортированных BPMN с форматом | Импорт = маппинг + отчёт о несоответствиях, не автоконвертация | Аналитик правит вручную в режиме аналитика |
| Pre-check блокирует публикацию из-за незаполненного реестра кухонь | Режим предупреждения на старте | Конфигурируемая строгость pre-check |
| Открытые архитектурные вопросы (Operation Catalog, словари) | Гибрид git+БД с критериями выбора | См. 4.4; на MVP — БД + аудит-лог |

## 6. Дорожная карта MVP → v1 → v2

### MVP (v0.1) — 5-7 недель

Критерии готовности:
- Аналитик импортирует существующий BPMN (TO BE супа), получает UI-модель
  и отчёт о несоответствиях v0.3
- Технолог создаёт процесс из шаблона (≥ 3 блоков из Operation Catalog)
- Создаёт ≥ 2 recipe на один шаблон (разные SKU, разные heat_time_sec)
  с валидацией типов и диапазонов
- Объявляет ≥ 2 сущности из словарей
- Dry-run валидация проходит без ошибок
- Публикация проходит pre-check реализуемости (в режиме предупреждения)
- Пилот запущен на 1 кухне, метрики собираются, критерий выхода задан
- Аудит-лог отвечает «кто и когда изменил target_temp_c» в один клик

Что входит:
- Режим технолога в общем редакторе (ролевая модель)
- Импорт BPMN → UI-модель
- Создание/клонирование из шаблона
- Формы recipe (сущность recipe, N на шаблон)
- Выбор process_entities из словарей
- Просмотр execution_contract
- Dry-run валидация + pre-check реализуемости
- Публикация версий, аудит-лог, пилотный контур

### v1 — 8-10 недель

Критерии готовности:
- Технолог настраивает рецептурные проверки (≥ 5 условий из allowed_outputs)
- Настраивает Quality Policy (лимиты, эскалации)
- Управляет изменениями (новая версия при изменении оборудования)
- Сравнивает версии визуально (diff схемы и параметров)

Что входит:
- Настройка проверок и шлюзов
- Настройка Quality Policy
- Управление изменениями, сравнение версий
- Миграция Operation Catalog на гибрид git+БД
