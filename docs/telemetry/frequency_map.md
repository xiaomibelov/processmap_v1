## 0. Метод и ОГРАНИЧЕНИЕ ДОСТУПА ⚠️

- `/api/admin/error-events` для technologist-demo → **403**. Доступ получен через
  прокси `GET /api/notifications/error_events` (org-scoped, org_default).
- **Видимый срез: 144 события (2026-06-15..07-31), все severity=error/fatal, org_default.**
  Владелец в админке видит **5124 события** — т.е. мы видим ~3% (одна демо-организация).
  Выводы T1–T4 валидны для org_default; переранжирование по полной выборке требует
  admin-токена ИЛИ запуска скрипта владельцем (`W4_EMAIL/W4_PASS` env, DAYS=60).
- Найдено и обойдено: offset-пагинация эндпоинта **нестабильна** (offset-обход терял
  события: 100 vs 144 при оконном обходе) — скрипт идёт суточными окнами
  `occurred_from/to` + dedupe по id. Зафиксировать как баг инструмента телеметрии
  (мини-трек: count-пагинация/курсор + группировка в админке — см. §6).

## 2. Сеансовые цепочки (T2)

### Цепочка 1 — сессия 1e4e833505: удалённая сессия, вечный polling + save в удалённую (06-26)
```

09:41:34  GET auto-pass/precheck → 404
09:41:34  GET note-aggregate   → 404
09:41:43  POST presence        → 404

09:41:56  GET  /sessions/{id}  → 404

```
Вывод: (а) фронт не прекращает polling (presence/meta/note-aggregate) при 404 — бесконечный
спам ошибок; (б) save в удалённую сессию даёт **409, а не 404** (CAS-guard срабатывает раньше
проверки существования) — пользователь видел бы «конфликт» вместо «сессия удалена».

## 6. Замечание по инструменту телеметрии (выбор зафиксирован)

- Выбран путь «скрипт поверх API» (не доработка админки сейчас): `fetch_error_events.mjs`.
- Баги инструмента, найденные по ходу (в мини-трек телеметрии): (1) нестабильная
  offset-пагинация (потеря событий при обходе — нужен курсор по occurred_at+id);
  (2) `count` в ответе = размер страницы, не total; (3) нет серверной группировки
  event_type × route × count — админка «dedupe off» не агрегирует;
  (4) самописец спамит 500 при своей недоступности (P-4).
