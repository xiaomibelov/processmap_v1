## Phase 0 (read-only) — подтверждение root cause на коде main

Root cause **подтверждён** на `origin/main@a74ac76b`:

1. `backend/app/routers/rag.py:28,171-175` — при `source_type=None` (unfiltered)
   вызывается `list_rag_chunks(org_id, limit=_MAX_CHUNKS_LOAD=2000)`.
2. `backend/app/rag/storage_rag.py:216` — ветка без фильтров:
   `SELECT * FROM rag_chunks WHERE org_id=? ORDER BY created_at LIMIT ?`
   → грузятся **2000 самых СТАРЫХ** чанков (`created_at` ASC по умолчанию).
3. Словарные корпуса (`glossary`, `property_dictionary`, `operation_catalog`)
   индексируются последними (STAGE_HYBRID_STATUS.md, 2026-09-07) → при >2000
   чанков, созданных раньше (в тестовой org 2067+ bpmn_xml от автоиндексации T4),
   все 34 словарных чанка вне окна → **unfiltered hit@3 = 0/8, оба режима
   (BM25 и hybrid), т.к. hybrid-нога оперирует тем же набором `chunks`**
   (`routers/rag.py:183` — `_hybrid_fused_results(..., chunks, ...)`).
4. Агент: `services/agent/memory/chat.py:576` (`_search_rag_for_structured_fact`,
   `source_type=""`) и `chat.py:103` — unfiltered fallback для словарей бесполезен.
5. Продуктовый `RagSearchPanel.jsx` (дефолт «все типы», `sourceType=""`) — тоже
   unfiltered, бьёт тот же путь.
6. `allowed_source_types` кодом поиска не читается — **не трогаем** (отозвано
   в STAGE_HYBRID_STATUS.md).
7. `bpmn_xml` растёт монотонно с каждой версией схемы (автоиндексация T4,
   `app/rag/indexer.py:58`) → без фикса словари **навсегда** невидимы для
   unfiltered-поиска.

### Обоснование выбора (a)

- Root cause — **смешение двух классов корпусов в одном FIFO-окне**: монотонно
  растущий `bpmn_xml` (по сути per-session исторический) и малые org-wide
  референс-словари. У них разные инварианты: словари должны быть видимы всегда,
  окно нужно только как защита памяти/латентности от роста bpmn_xml.
- (a) разделяет эти классы на уровне SQL-загрузки — единственной точке, где
  ещё не поздно (post-LIMIT фильтрация невозможна).
- Не меняет HTTP-контракт: параметры и схема ответа `GET /api/rag/search`
  прежние → **OpenAPI gate §6.1 не применим** (эндпоинты не добавляются/не
  меняются; см. п.5 задачи — подтверждено, спека не регенерируется).

## План реализации (после approve)

1. `backend/app/rag/storage_rag.py` — в ветке без фильтров грузить:
   - чанки референс-типов `REFERENCE_SOURCE_TYPES = {"glossary", "property_dictionary", "operation_catalog"}` — целиком (LIMIT снимается);
   - остальные — с прежним окном `_MAX_CHUNKS_LOAD` (ORDER BY created_at ASC поведение для bpmn_xml сохраняем как есть; см. примечание ниже);
   - объединение двух SELECT'ов (JOIN с `rag_documents`, `is_active=1` — заодно
     чинит молчаливое чтение неактивных документов в unfiltered-ветке).
   Примечание: DESC для bpmn_xml НЕ вводим в этом контуре (минимальный патч);
   при желании — отдельный контур.
2. `backend/app/routers/rag.py` — при необходимости точечная адаптация вызова
   (предпочтительно: сигнатура `rag_search` не меняется, логика инкапсулирована
   в `list_rag_chunks`; cap применяется к не-референс части).
3. **Регрессионный тест** (`backend/tests/test_rag_fullcorpus_window.py`):
   org с >2000 bpmn-чанков (синтетика, старые `created_at`) + несколько
   glossary-чанков (новые) → запрос к glossary обязан давать hit
   **в обоих режимах**: BM25 (`hybrid_enabled=0`) и hybrid (`hybrid_enabled=1`,
   embedder замокан/деградирован). Плюс контроль: старые bpmn-чанки вне окна
   по-прежнему не грузятся (cap сохранён).
4. **Бенч до/после** (latency + память полнокорпусного поиска): прогон
   `bench_fullcorpus_load.py` до патча (есть, выше) и после — сравнение
   в `EXEC_REPORT.md`; цель — регресс ≤10% по времени полного прохода.
5. Тесты backend + 5-plane proof (code / workspace / DB / env / serving).
6. PR на русском, merge — только по approve. После merge — проверка на stage:
   unfiltered hit@3 q8–q15 = **8/8** без фильтров (методология из

## Follow-ups (вне scope, кандидаты в бэклог)

- **Кэш BM25-индекса по версии корпуса** — per-request пересборка BM25 доминирует

  при переиндексации. Кандидат в бэклог, отдельный контур.
- **Pre-existing баг (не из этого контура):** `test_rag_settings_runtime` —
  6 падений на чистом origin/main: `sqlite3.ProgrammingError: type 'Query' is not

  `list_rag_chunks` утекает FastAPI `Query`-дефолт). Воспроизведено до и после
  патча идентично. Отдельный fix-контур.

  старые чанки корпуса выпадут из unfiltered-окна. При появлении больших
  референс-корпусов — отдельный cap/стратегия.
